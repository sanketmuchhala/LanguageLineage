ONNX Runtime loads an .onnx model into an in-memory computation graph inside its C++ InferenceSession, runs provider-independent Basic graph optimizations (constant folding, redundant node elimination, and basic fusions), and then partitions the graph across registered Execution Providers in priority order using GetCapability(). On the CPU and CUDA providers it applies Extended graph optimizations (such as Attention and LayerNorm fusion) before running C++ kernels or CUDA / cuDNN / cuBLAS kernels; with the TensorRT provider, supported subgraphs are compiled into an NVIDIA TensorRT engine while unsupported operators fall back to CUDA or the CPU.

The selected path, step by step

  1. Your application passes model path to ONNX model (.onnx): Your application passes the .onnx model file (or bytes) and the priority-ordered execution provider list when creating an InferenceSession.
  2. ONNX model (.onnx) loaded into InferenceSession: InferenceSession parses the ONNX protobuf graph, operator nodes, and initializers into ONNX Runtime's in-memory Graph representation.
  3. InferenceSession runs level-1 passes in Basic graph passes: Before partitioning the graph across providers, ONNX Runtime applies Basic graph optimizations such as constant folding, dead-node elimination, and Conv+Add fusion.
  4. Basic graph passes handed to GetCapability split: The simplified graph is passed to ONNX Runtime's graph partitioner to assign nodes or subgraphs to registered execution providers.
  5. GetCapability split fuses CPU/CUDA nodes in Extended & layout opt: For nodes assigned to the CPU or CUDA execution providers, ONNX Runtime runs Extended graph optimizations (complex node fusions) and CPU layout optimizations.
  6. Extended & layout opt dispatches GPU nodes to CUDA EP (cuDNN/CUDA): Nodes claimed by CUDAExecutionProvider (including fused Attention, LayerNorm, and BiasGelu nodes) run through the CUDA execution provider.
  7. GetCapability split unclaimed ops fall back to CPU EP kernels: Any operator node not supported by the GPU execution providers is assigned to the built-in CPUExecutionProvider.
  8. CUDA EP (cuDNN/CUDA) launches CUDA/cuDNN kernels on NVIDIA GPU: The CUDA execution provider launches CUDA, cuDNN, and cuBLAS kernels on the NVIDIA GPU.
  9. CPU EP kernels runs on CPU: The CPU execution provider runs its C++ kernels on the host CPU.

Why graph optimizations happen in two stages

ONNX Runtime splits graph transformations into levels that run before and after hardware partitioning. Basic graph optimizations—constant folding, dead-node elimination, and simple operator fusions like Conv+Add—are semantics-preserving rewrites that run before partitioning, so every execution provider benefits from them.

Extended graph optimizations (such as multi-node Attention, LayerNorm, and Bias+GELU fusions) and NCHWc layout transformations run after GetCapability() partitioning, because they emit fused operator nodes implemented specifically by the CPU, CUDA, or ROCm execution providers.

How GetCapability() partitions a model with fallbacks

Unlike a single-backend engine, an ONNX Runtime session takes a priority-ordered list of execution providers—for example, TensorrtExecutionProvider, then CUDAExecutionProvider, then CPUExecutionProvider. ONNX Runtime queries each provider's GetCapability() interface in order to claim subgraphs or individual nodes.

Any operator that a higher-priority accelerator provider cannot run is automatically assigned to the next provider in the list, with the built-in CPU execution provider acting as the final fallback.

What is the difference between ONNX and ONNX Runtime?

An ONNX file describes a computation in a portable graph format. ONNX Runtime supplies the machinery to load and execute that graph. Exporting a PyTorch model to ONNX does not leave the ordinary PyTorch eager interpreter in charge of numerical execution. The Python API overview describes sessions, inputs, outputs and provider configuration.

A session is worth distinguishing from one inference call. Session initialization can parse the model, apply optimizations and prepare provider assignments. Repeated session.run calls then use that prepared configuration. Recreating the session for every request measures more than model execution.

Why does ONNX Runtime still use the CPU with CUDA?

Execution providers advertise the operators or subgraphs they can handle. ONNX Runtime considers them in priority order. With CUDA before CPU, supported operations can go to CUDA while other supported CPU operations remain on the host. The architecture document explains this partitioning rather than treating the entire model as an indivisible GPU job.

The CUDA and TensorRT selections retain fallback paths because provider registration does not prove complete operator coverage. The diagram shows possible fallback work, not a measurement that every model necessarily executes on both processors. If the installed package cannot load CUDA dependencies, that is a provider-availability problem, distinct from an individual operator being assigned to the CPU.

Does graph optimization compile every model into one GPU kernel?

No. Graph optimizations include simplifications and selected fusions, and the available transformations depend on provider and optimization level. Some occur before partitioning; others operate on provider-assigned graph portions. The optimization box is a summary of this preparation work, not a promise of one fused executable. Read the optimization guide before assuming a particular fusion is enabled.

Optimizations can run at session initialization or be saved in an optimized model ahead of deployment. Offline optimization must match the target options and hardware constraints. An optimized artifact for one provider or CPU instruction set is not automatically portable to every other environment.

Why can data transfers matter as much as compute?

The default Python API commonly accepts and returns host-resident data. For GPU execution this can introduce transfers between host and device. I/O binding allows the application to manage device-resident inputs and outputs. It changes where the data lives, rather than changing the model into a different neural network. See the I/O binding examples in the API overview.

How is CUDA different from the TensorRT execution provider?

CUDAExecutionProvider and TensorRTExecutionProvider are distinct plugins in the execution-provider catalog. The controls preserve separate CPU, CUDA and TensorRT provider paths. The TensorRT execution provider can compile supported graph partitions into an engine, while other operations can use fallback providers. Also distinguish this integration from TensorRT-LLM, which is a separate serving stack with its own current PyTorch execution backend.

ONNX model (.onnx)

model format

A serialized ONNX computation graph containing standard operators, tensor types, and constant weight initializers exported from PyTorch, TensorFlow, or scikit-learn.

  • ONNX provides an open source format for AI models, both deep learning and traditional ML. It defines an extensible computation graph model, as well as definitions of built-in operators and standard data types.
    ONNX README (onnx/onnx) Source repository
  • supporting models from deep learning frameworks such as PyTorch and TensorFlow/Keras as well as classical machine learning libraries such as scikit-learn, LightGBM, XGBoost, etc.
    ONNX Runtime README (microsoft/onnxruntime) Source repository

InferenceSession

runtime

ONNX Runtime's C++ session engine. When initialized, it parses the model into an in-memory graph, runs graph optimizations, and coordinates execution providers.

In the atlas: C++

  • ONNX Runtime is compatible with different hardware, drivers, and operating systems, and provides optimal performance by leveraging hardware accelerators where applicable alongside graph optimizations and transforms.
    ONNX Runtime README (microsoft/onnxruntime) Source repository
  • In online mode, when initializing an inference session, we also apply all enabled graph optimizations before performing model inference.
    Graph Optimizations in ONNX Runtime (ONNX Runtime documentation) Project docs

Basic graph passes

compiler

Level-1 semantics-preserving graph rewrites—constant folding, redundant node elimination, and Conv/Add/BatchNorm fusions—applied before partitioning.

  • These are semantics-preserving graph rewrites which remove redundant nodes and redundant computation. They run before graph partitioning and thus apply to all the execution providers.
    Graph Optimizations in ONNX Runtime (ONNX Runtime documentation) Project docs
  • Constant Folding: Statically computes parts of the graph that rely only on constant initializers.
    Graph Optimizations in ONNX Runtime (ONNX Runtime documentation) Project docs

GetCapability split

framework component

Queries registered execution providers via GetCapability() in priority order to allocate supported subgraphs or nodes to each provider.

In the atlas: C++

  • ONNX Runtime works with the execution provider(s) using the GetCapability() interface to allocate specific nodes or sub-graphs for execution by the EP library in supported hardware.
    ONNX Runtime Execution Providers (ONNX Runtime documentation) Project docs

Extended & layout opt

compiler

Post-partitioning complex operator fusions (Attention, LayerNormalization, SkipLayerNorm, BiasGelu on CPU/CUDA) and NCHWc data layout transforms on CPU.

  • These optimizations include complex node fusions. They are run after graph partitioning and are only applied to the nodes assigned to the CPU or CUDA or ROCm execution provider.
    Graph Optimizations in ONNX Runtime (ONNX Runtime documentation) Project docs
  • NCHWc Optimizer: Optimizes the graph by using NCHWc layout instead of NCHW layout.
    Graph Optimizations in ONNX Runtime (ONNX Runtime documentation) Project docs

TensorRT EP

compiler

Compiles supported ONNX subgraphs into optimized NVIDIA TensorRT engines for the target GPU.

  • The TensorRT execution provider in the ONNX Runtime makes use of NVIDIA’s TensorRT Deep Learning inferencing engine to accelerate ONNX model in their family of GPUs.
    TensorRT Execution Provider (ONNX Runtime documentation) Project docs

CUDA EP (cuDNN/CUDA)

kernel

Runs assigned operators on the NVIDIA GPU using precompiled CUDA kernels and NVIDIA libraries including cuDNN, cuBLAS, and cuBLASLt.

In the atlas: CUDA

  • The CUDA Execution Provider enables hardware accelerated computation on Nvidia CUDA-enabled GPUs.
    CUDA Execution Provider (ONNX Runtime documentation) Project docs
  • libcudart 11.4.43 libcufft 10.5.2.100 libcurand 10.2.5.120 libcublasLt 11.6.5.2 libcublas 11.6.5.2 libcudnn 8.2.4
    CUDA Execution Provider (ONNX Runtime documentation) Project docs

CPU EP kernels

kernel

ONNX Runtime's built-in C++ CPU execution provider. Runs the full graph on CPU or any operator nodes not claimed by a higher-priority GPU provider.

In the atlas: C++

  • The ONNX Runtime package can be built with any combination of the EPs along with the default CPU execution provider.
    ONNX Runtime Execution Providers (ONNX Runtime documentation) Project docs
  • For example ['CUDAExecutionProvider', 'CPUExecutionProvider'] means execute a node using CUDAExecutionProvider if capable, otherwise execute using CPUExecutionProvider.
    ONNX Runtime Execution Providers (ONNX Runtime documentation) Project docs

CPU

hardware

The host CPU executing the CPU execution provider's C++ kernels.

  • This architecture abstracts out the details of the hardware specific libraries that are essential to optimize the execution of deep neural networks across hardware platforms like CPU, GPU, FPGA or specialized NPUs.
    ONNX Runtime Execution Providers (ONNX Runtime documentation) Project docs

NVIDIA GPU

hardware

The NVIDIA GPU executing compiled TensorRT engines and CUDA / cuDNN / cuBLAS kernels.

  • The CUDA Execution Provider enables hardware accelerated computation on Nvidia CUDA-enabled GPUs.
    CUDA Execution Provider (ONNX Runtime documentation) Project docs

What this does not show

Documented inference paths for an ONNX (.onnx) model in ONNX Runtime using three execution providers: the default CPU provider, the NVIDIA CUDA provider, and the NVIDIA TensorRT provider. Other execution providers (CoreML, DirectML, OpenVINO, QNN, ROCm, WebGPU) and ONNX Runtime Training are out of scope. ONNX Runtime uses the same GetCapability() partitioning architecture for more than a dozen other execution providers, including CoreML, DirectML, OpenVINO, and WebGPU.
