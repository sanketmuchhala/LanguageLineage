A request to SGLang's HTTP server goes to the TokenizerManager in the same process, which tokenizes it and sends it over ZMQ to the Scheduler process. The scheduler matches the prompt against the radix prefix cache (RadixAttention), so tokens shared with earlier requests are not prefilled again, forms a batch and runs it through the ModelRunner. Decode steps replay CUDA graphs, and attention runs on the backend SGLang picks for your GPU: FlashInfer on Ampere and Ada, FlashAttention 3 on Hopper, TRT-LLM MHA on Blackwell. Output tokens go to the DetokenizerManager process, which returns text to be streamed back.

The selected path, step by step

  1. Your app or client sends a request to HTTP server: Your client sends an HTTP request to the server.
  2. HTTP server hands the request to TokenizerManager: The HTTP server and the TokenizerManager share the main process.
  3. TokenizerManager sends tokens over ZMQ to Scheduler: Tokenized requests go to the scheduler process over ZMQ.
  4. Scheduler matches prefixes in Radix prefix cache: The scheduler matches each request against the cached prefixes, so the KV cache of tokens shared with earlier requests is reused rather than computed again.
  5. Scheduler forwards each batch to ModelRunner: The scheduler forms a batch and runs it through the model.
  6. ModelRunner replays decode steps as Decode CUDA graphs: Decode batches replay captured CUDA graphs, one per batch shape by default.
  7. ModelRunner computes attention with FlashAttention 3: With no --attention-backend set, Hopper GPUs use FlashAttention 3.
  8. FlashAttention 3 runs on NVIDIA GPU: The attention kernels run on the GPU.
  9. Decode CUDA graphs replayed on NVIDIA GPU: Replaying a graph launches the step's kernels together.
  10. Scheduler sends output tokens to DetokenizerManager: Output tokens go to the detokenizer process.
  11. DetokenizerManager returns text to TokenizerManager: Decoded text goes back to the TokenizerManager, which returns it to the client.

Why prefix caching matters

When many requests share the same prefix, the KV cache for that prefix is identical. SGLang keeps the KV cache of those tokens in a radix tree, where each node covers a span of tokens and a path from the root is a request's prefix. A new request that shares the path skips computing it, and the shared nodes are stored once.

How this compares with vLLM

Both engines split serving into processes: SGLang uses a TokenizerManager, a scheduler process and a DetokenizerManager talking over ZMQ; vLLM uses an API server, an engine core and GPU workers. Both replay CUDA graphs and choose an attention backend by GPU. Which one is faster depends on the workload and version, so this page does not compare speed.

Radix prefix cache

framework component

RadixAttention's radix tree over the KV cache: each node holds the KV of a span of tokens, so requests that share a prefix reuse it instead of recomputing it.

In the atlas: SGLang

  • The radix tree data structure for managing the KV cache.
    python/sglang/srt/mem_cache/radix_cache.py (sgl-project/sglang) Source repository
  • In RadixAttention, each node of the RadixTree corresponds to the KV cache of a consecutive span of tokens in GPU memory.
    HiCache design (SGLang documentation source) Source repository

FlashInfer

kernel

Default attention backend for standard (MHA) models on Ampere, Ada and other non-Hopper, non-Blackwell NVIDIA GPUs, when available.

  • Defaults to flashinfer if available; otherwise falls back to triton.
    Attention backend (SGLang documentation source) Source repository

FlashAttention 3

kernel

Default attention backend on Hopper GPUs (H100, H200) with CUDA 12.3 or newer, for supported models.

  • Defaults to fa3 if using CUDA 12.3+ and the model configuration is supported.
    Attention backend (SGLang documentation source) Source repository

TRT-LLM MHA

kernel

Default attention backend on Blackwell GPUs (B200), unless speculative decoding uses topk > 1.

  • Defaults to trtllm_mha, unless using speculative decoding with topk > 1.
    Attention backend (SGLang documentation source) Source repository

NVIDIA GPU

hardware

The GPU that runs the batch.

  • If the --attention-backend argument is not specified, SGLang automatically selects the best backend based on the hardware (CUDA) and model architecture.
    Attention backend (SGLang documentation source) Source repository

What this does not show

Documented paths for one standard (MHA) model such as Llama or Qwen served on a single NVIDIA GPU with default settings, by GPU generation. MLA models, AMD and other hardware, tensor and data parallelism, speculative decoding, HiCache's host and remote tiers, the optional torch.compile mode and SGLang's frontend language are out of scope.
