What Actually Happens When TensorRT-LLM Runs a Model?

A call to LLM.generate() or trtllm-serve tokenizes the prompt and submits it to a per-rank PyExecutor worker running an asynchronous loop with the Overlap Scheduler. Each step, C++-bound CapacityScheduler and MicroBatchScheduler pick active context and generation requests while the C++-bound KVCacheManager allocates paged KV-cache blocks. ModelEngine delegates the batch to a native PyTorch model (PyTorch is now TensorRT-LLM's sole execution backend; `trtllm-build` engines were removed). With Piecewise CUDA Graph enabled, TorchDynamo traces the model into Torch IR and TensorRT-LLM's custom torch.compile backend lowers it via aot_module_simplified to ATen IR—fusing AllReduce + RMSNorm and scheduling multiple CUDA streams without using TorchInductor—then replays Piecewise CUDA Graphs around in-place TrtllmAttention or FlashInferAttention kernels.

The selected path, step by step

  1. LLM API / serve tokenizes and submits request to PyExecutor worker: LLM.generate() or trtllm-serve tokenizes the prompt and queues the request for the rank's PyExecutor worker.
  2. PyExecutor worker schedules active requests via C++ batch scheduler: At each iteration of its background loop, PyExecutor invokes SimpleScheduler (combining CapacityScheduler and MicroBatchScheduler).
  3. C++ batch scheduler checks capacity and reserves blocks in C++ KVCacheManager: CapacityScheduler queries KVCacheManager for available blocks and PyExecutor calls prepare_resources to allocate paged KV-cache blocks for the batch.
  4. C++ KVCacheManager passes scheduled batch & KV buffers to ModelEngine & runner: PyExecutor invokes ModelEngine.forward with the scheduled context and generation requests and their allocated KV-cache resources.
  5. ModelEngine & runner runs forward pass on PyTorch model: ScheduledModelRunner prepares the input tensors and executes the PyTorch model's forward pass.
  6. PyTorch model invokes attention through Attention custom op: Each transformer layer prepares AttentionMetadata and calls the wrapped attention custom op.
  7. PyTorch model traced in fullgraph mode by TorchDynamo (FX): Enabling prefill_cuda_graph_backend: piecewise enables torch.compile, which traces the decoder model with TorchDynamo into a Torch IR FX graph.
  8. TorchDynamo (FX) lowered via aot_module_simplified to TRT-LLM ATen IR: TensorRT-LLM's custom backend lowers the FX graph to ATen IR, fuses AllReduce + Residual + RMSNorm, removes mutation-wrapper copies, and inserts multi-stream scheduling ops.
  9. TRT-LLM ATen IR partitioned at attention into Piecewise CUDA Graph: Non-capturable attention is split out while the surrounding fused ATen/custom-op segments are captured per token-count bucket as Piecewise CUDA Graphs.
  10. Attention custom op dispatches by default to TrtllmAttention: By default, AttentionBackend.forward dispatches to TrtllmAttention, reading and updating paged KV cache blocks.
  11. Piecewise CUDA Graph produces logits for Sampler: After replaying the Piecewise or generation CUDA Graph segments, the model forward outputs logits to the asynchronous Sampler.
  12. TrtllmAttention executes CUDA kernels on NVIDIA GPU: TrtllmAttention launches its custom CUDA attention kernels on the GPU, writing in-place into preallocated buffers during Piecewise CUDA Graph execution.
  13. Sampler samples next tokens on NVIDIA GPU: Sampling runs asynchronously on the GPU while the Overlap Scheduler processes the previous step's completed tokens on the CPU.

PyTorch is now the sole execution backend

Early releases of TensorRT-LLM required converting weights and running `trtllm-build` to compile a closed TensorRT `.engine` plan file ahead of time. TensorRT-LLM has since removed the TensorRT engine backend entirely: PyTorch is now the sole execution backend, HuggingFace checkpoints load directly into `tensorrt_llm.LLM`, and models are written in native PyTorch under `tensorrt_llm/_torch/models/`.

Inside each rank's `PyExecutor` worker, latency-critical control-plane pieces—the two-stage in-flight batching scheduler (`CapacityScheduler` and `MicroBatchScheduler`) and the paged `KVCacheManager`—run through C++ bindings (`cpp/tensorrt_llm/`), while the Overlap Scheduler launches step $n+1$ on the GPU before the CPU finishes post-processing step $n$.

How TensorRT-LLM's torch.compile backend differs from vLLM's

Both vLLM and TensorRT-LLM use PyTorch's TorchDynamo to capture the model graph and split it around attention for Piecewise CUDA Graphs, but what happens after Dynamo is different. vLLM hands each subgraph to TorchInductor to generate fused Triton kernels.

TensorRT-LLM does not use TorchInductor. Its custom `torch.compile` backend calls `aot_module_simplified` to lower the FX graph to ATen IR, runs custom pattern-matcher passes to fuse cross-module `AllReduce + Residual + RMSNorm` (+ FP8/FP4 quantization) into custom CUDA ops, strips `auto_functionalize` mutation copies in-place, inserts `trtllm.set_stream` / `record_event` / `wait_event` ops for multi-stream execution, and rewrites attention to write in-place into preallocated CUDA Graph buffers.

Every stage

LLM API / serve

application

Your Python code calling LLM.generate() or an OpenAI-compatible HTTP client calling trtllm-serve. The LLM class handles tokenization and detokenization.

In the atlas: Python

  • The `LLM` class is a core entry point for the TensorRT LLM, providing a simplified `generate()` API for efficient large language model inference.
    Architecture Overview (TensorRT-LLM Developer Guide) Source repository
  • The `LLM` class automatically manages essential pre and post-processing steps, including tokenization (encoding input prompts into numerical representations) and detokenization (decoding model outputs back into human-readable text).
    Architecture Overview (TensorRT-LLM Developer Guide) Source repository
  • You can use the `trtllm-serve` command to start an OpenAI compatible server to interact with a model.
    Quick Start Guide (TensorRT-LLM documentation) Source repository

PyExecutor worker

runtime

A dedicated worker process per rank running an asynchronous background loop, with the Overlap Scheduler enabled by default to overlap CPU post-processing with GPU execution.

In the atlas: TensorRT-LLM

  • Internally, the `LLM` class orchestrates the creation of a dedicated `PyExecutor(Worker)` process on each rank.
    Architecture Overview (TensorRT-LLM Developer Guide) Source repository
  • This `PyExecutor` operates in a continuous background loop, designed for the efficient, asynchronous processing of inference requests.
    Architecture Overview (TensorRT-LLM Developer Guide) Source repository
  • The Overlap Scheduler maximizes GPU utilization by hiding CPU-bound latency behind GPU computation.
    Architecture Overview (TensorRT-LLM Developer Guide) Source repository

C++ batch scheduler

framework component

Two-stage C++-bound scheduler (CapacityScheduler and MicroBatchScheduler) that dynamically selects context and generation requests at every step.

In the atlas: C++

  • TensorRT LLM PyTorch backend employs inflight batching, a mechanism where batching and scheduling occur dynamically at each LLM step.
    Scheduler (TensorRT-LLM PyTorch Backend documentation) Source repository
  • Both CapacityScheduler and MicroBatchScheduler currently use C++ bindings.
    Architecture Overview (TensorRT-LLM PyTorch Backend documentation) Source repository

C++ KVCacheManager

framework component

C++-bound resource manager that allocates, updates, and recycles paged KV-cache blocks for the scheduled context and generation requests.

In the atlas: C++

  • Currently, the KVCacheManager uses C++ binding.
    Architecture Overview (TensorRT-LLM PyTorch Backend documentation) Source repository
  • In `KVCacheManager`, this involves allocating KV Cache memory. This allocation varies depending on the request type.
    KV Cache Manager (TensorRT-LLM PyTorch Backend documentation) Source repository

ModelEngine & runner

framework component

Loads the model, builds ScheduledInputs for the current step, and delegates input preparation, CUDA graphs, and execution to ScheduledModelRunner.

In the atlas: TensorRT-LLM

  • `PyExecutor` calls `ModelEngine.forward` with scheduled requests, runtime resources, and the current speculative decoding state; the engine builds `ScheduledInputs` and delegates to a `ScheduledModelRunner`.
    Architecture Overview (TensorRT-LLM PyTorch Backend documentation) Source repository
  • The concrete runner owns input preparation, model execution, CUDA graphs, metadata, and output processing.
    Architecture Overview (TensorRT-LLM PyTorch Backend documentation) Source repository

PyTorch model

framework component

The model defined in native PyTorch under tensorrt_llm/_torch/models/. PyTorch is the sole execution backend of TensorRT-LLM; HuggingFace checkpoints load directly without an engine build step.

In the atlas: PyTorch

  • PyTorch is the sole execution backend of TensorRT LLM; the former TensorRT engine backend has been removed
    Architecture Overview (TensorRT-LLM PyTorch Backend documentation) Source repository
  • There is no separate checkpoint-conversion or engine-build step.
    Migration Guide: TensorRT Backend Removed (TensorRT-LLM documentation) Source repository

Eager prefill ops

kernel

Without Piecewise CUDA Graphs, context and mixed batches execute the PyTorch decoder eagerly while generation-only CUDA graphs are captured from the eager decoder.

In the atlas: CUDA

  • With this option enabled, ineligible context and mixed forwards use the eager decoder. Ordinary CUDA graphs are also captured from the eager decoder and subsequently replayed as CUDA graphs.
    Torch Compile & Prefill CUDA Graph (TensorRT-LLM documentation) Source repository

Attention custom op

framework component

Attention is wrapped as an opaque PyTorch custom op with a fake kernel and AttentionMetadata, writing in-place into preallocated tensors so Piecewise CUDA Graph segments keep stable addresses.

In the atlas: TensorRT-LLM

  • Clear the boundary of attention so that it can be easily recognized by Piecewise CUDA Graph
    Torch Compile & Prefill CUDA Graph (TensorRT-LLM documentation) Source repository
  • Instead of allocating its own output, attention writes results into a tensor preallocated by the preceding CUDA Graph segment.
    Torch Compile & Prefill CUDA Graph (TensorRT-LLM documentation) Source repository

TorchDynamo (FX)

compiler

Traces the PyTorch model in fullgraph mode into a Torch IR FX graph, preserving tensor names so the compiler can track the dynamic token-count SymInt.

In the atlas: PyTorch

  • Torch IR is the Fx graph that is directly traced by Torch Dynamo.
    Torch Compile & Prefill CUDA Graph (TensorRT-LLM documentation) Source repository
  • For Piecewise CUDA Graph, it needs to find the correct `SymInt` which represents the token number.
    Torch Compile & Prefill CUDA Graph (TensorRT-LLM documentation) Source repository

TRT-LLM ATen IR

compiler

Lowers Torch IR via aot_module_simplified to ATen IR, fuses AllReduce + Residual + RMSNorm (+ FP8/FP4), strips auto_functionalize copies in-place, and schedules multi-stream ops without using TorchInductor.

In the atlas: TensorRT-LLM

  • We get ATen IR after explicitly calling `aot_module_simplified` on the Fx graph.
    Torch Compile & Prefill CUDA Graph (TensorRT-LLM documentation) Source repository
  • We mainly do the operation fusion for AllReduce & RMSNorm.
    Torch Compile & Prefill CUDA Graph (TensorRT-LLM documentation) Source repository
  • In a TorchInductor pipeline, later passes typically eliminate this copy, but TensorRT LLM relies on custom ops and does not use Inductor.
    Torch Compile & Prefill CUDA Graph (TensorRT-LLM documentation) Source repository

TrtllmAttention

kernel

The default production attention backend (TrtllmAttention): custom CUDA kernels supporting inflight batching, paged KV cache, fused QKV input, and FP8 output.

In the atlas: CUDA

  • The TRT-LLM backend, `TrtllmAttention`, serves as the default backend and supports all the features available in the Flashinfer backend while being further optimized for enhanced performance.
    Attention (TensorRT-LLM PyTorch Backend documentation) Source repository
  • It can accept a single QKV tensor as input, which is more efficient compared to using separate Q, K, and V tensors.
    Attention (TensorRT-LLM PyTorch Backend documentation) Source repository

FlashInferAttention

kernel

Optional FlashInfer attention backend (selected with attn_backend="flashinfer") supporting inflight batching, paged KV cache, FP8 quantization, and RoPE fusion.

In the atlas: CUDA

  • In contrast, the Flashinfer backend, `FlashInferAttention`, is performance-optimized and supports both inflight batching and paged KV cache.
    Attention (TensorRT-LLM PyTorch Backend documentation) Source repository
  • By integrating rotary position embedding (RoPE) directly into the attention computation, this feature enhances efficiency and reduces overhead.
    Attention (TensorRT-LLM PyTorch Backend documentation) Source repository

Piecewise CUDA Graph

runtime

Context and mixed batches pad the token count and replay captured Piecewise CUDA Graph segments around eager attention; pure generation iterations replay generation-only CUDA Graphs.

In the atlas: CUDA

  • We implement Piecewise CUDA Graph execution on top of torch.compile: non-capturable regions run in eager mode, while the rest of the model is captured and replayed as CUDA Graph segments.
    Torch Compile & Prefill CUDA Graph (TensorRT-LLM documentation) Source repository
  • Piecewise CUDA Graph only handles context-only and mixed context+generation iterations, while the generation-only CUDA Graph only handles pure generation iterations.
    Torch Compile & Prefill CUDA Graph (TensorRT-LLM documentation) Source repository

Decode CUDA Graph

runtime

Pure generation steps replay captured CUDA Graphs padded to the nearest supported batch size, launching the entire sequence of decode kernels with one API call.

In the atlas: CUDA

  • By capturing a sequence of CUDA operations as a single graph, the entire sequence can be launched with one API call, minimizing CPU-GPU synchronization and driver overhead.
    Architecture Overview (TensorRT-LLM Developer Guide) Source repository
  • If an incoming batch's size doesn't match a captured graph, it's padded to the nearest larger, supported size for which a graph exists.
    Architecture Overview (TensorRT-LLM Developer Guide) Source repository

Sampler

framework component

Applies greedy, top-k, top-p, or beam-search sampling to the raw logits from ModelEngine asynchronously while the Overlap Scheduler processes the previous batch.

In the atlas: TensorRT-LLM

  • `Sampler`: Takes the raw outputs (logits) from the ModelEngine and applies appropriate sampling strategies (e.g., greedy, top-k, top-p, beam search) to generate the final output tokens.
    Architecture Overview (TensorRT-LLM Developer Guide) Source repository
  • The key strategy is to launch the GPU's work for the next step (n+1) immediately, without waiting for the CPU to finish processing the results of the current step (n).
    Architecture Overview (TensorRT-LLM Developer Guide) Source repository

NVIDIA GPU

hardware

Executes the replayed CUDA Graph segments, custom CUDA kernels (attention, GEMM, MoE, AllReduce), and asynchronous sampling on NVIDIA GPUs.

  • `ModelEngine`: Handles the loading and highly efficient execution of the language model on the GPU hardware.
    Architecture Overview (TensorRT-LLM Developer Guide) Source repository

What this does not show

Documented execution paths for a causal LLM running on an NVIDIA GPU in TensorRT-LLM's PyTorch backend (the sole execution backend after the legacy TensorRT engine backend was removed), in either torch.compile + Piecewise CUDA Graph mode or default eager-prefill + generation CUDA Graph mode, using the default TrtllmAttention or FlashInferAttention backend. Multi-node tensor/pipeline/expert parallelism, DeepGEMM/MegaMoE barrier internals, speculative decoding, visual diffusion models (VisualGen), the experimental breakable CUDA Graph backend, and the removed legacy trtllm-build TensorRT engine pipeline are out of scope. The removed legacy TensorRT engine backend (`trtllm-build` / `LLM(backend="tensorrt")`) and closed NVIDIA TensorRT compiler internals are out of scope; TensorRT-LLM's migration guide states that PyTorch is now the sole execution backend.
