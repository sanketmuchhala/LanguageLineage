Current TensorRT-LLM uses a PyTorch execution backend. A Python LLM call or a request to trtllm-serve enters an executor that schedules requests, manages resources and runs the model forward pass using optimized GPU kernels. Older instructions built around the removed TensorRT engine backend describe a different version of the system. An API-compatible server also does not reveal the internals of any unrelated hosted service.

  6. Specialized kernels launches device work NVIDIA GPU: The executor uses CUDA runtime bindings for the supported NVIDIA GPU execution path.

Is TensorRT-LLM the same product as TensorRT?

No. TensorRT-LLM is an LLM inference stack with its own model API, executor and scheduling. The [migration guide](https://nvidia.github.io/TensorRT-LLM/latest/legacy/tensorrt-backend-removal.html) says the legacy TensorRT engine backend has been removed and PyTorch is now the sole execution backend. A familiar product name is not sufficient evidence that a current request first runs trtllm-build.

This version boundary matters when following tutorials. Historical conversion and engine-build instructions can be correct for earlier releases while failing to describe the current API. Match the documentation to the installed version before copying commands or assuming one fixed execution architecture.

What happens after the request arrives?

The [quick-start guide](https://nvidia.github.io/TensorRT-LLM/latest/quick-start-guide.html) documents Python LLM calls and HTTP serving with trtllm-serve. These are entry points to the inference stack. A compatible HTTP endpoint specifies how a client talks to the server; it does not make the server another vendor’s model service.

The [architecture overview](https://nvidia.github.io/TensorRT-LLM/latest/torch/arch_overview.html) describes PyExecutor, its model engine and decoding responsibilities. The diagram shows the compute route for one scheduled forward iteration. After model outputs are available, the decoder produces tokens and request state is updated; generation repeats rather than returning to the initial loading step for every token.

What is inflight batching?

The [scheduler documentation](https://nvidia.github.io/TensorRT-LLM/latest/torch/scheduler.html) describes scheduling at each LLM step. CapacityScheduler determines resource fit, including cache capacity. MicroBatchScheduler chooses which fitting requests should actually execute next. This allows an active server to reconsider runnable work across iterations instead of assuming one fixed request batch lasts forever.

Resource fit and execution selection are related but distinct. A request can be active without being chosen for the current forward pass. The diagram therefore puts scheduling before model execution; it does not claim that every queued request runs simultaneously or that batching removes latency tradeoffs.

Where do Python, C++ and CUDA appear?

Python is visible in the executor and model-facing interfaces. The architecture documents C++ bindings for scheduler and KV-cache components, and the [executor source](https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/_torch/pyexecutor/py_executor.py) imports CUDA runtime bindings. Numerical execution uses the optimized kernel stack described in the [project overview](https://github.com/NVIDIA/TensorRT-LLM/blob/main/README.md).

These are different responsibilities. A Python implementation edge describes orchestration; a C++ binding does not mean every kernel is C++; and selecting the PyTorch backend does not mean TensorRT-LLM becomes an ordinary unoptimized eager Python loop. Kernel selection and supported model details depend on the actual release and configuration.

How does this compare with vLLM or llama.cpp?

Compare the documented mechanisms rather than treating the engines as aliases. vLLM has its own scheduling and execution stack. llama.cpp uses a distinct model/runtime/backend arrangement. This page explains current TensorRT-LLM execution without asserting a universal speed winner or publishing workload-free performance rankings.

Does the diagram describe every token and every GPU?

No. It stops at the hardware work for a scheduled forward iteration. Sampling, caching, repeated decoding and advanced multi-device scheduling add further state transitions. A complete deployment must satisfy supported hardware, model and software requirements; the diagram is a cited architectural trace, not a compatibility certification.

What this does not show

Current TensorRT-LLM documentation retrieved in November 2026, after removal of the legacy TensorRT engine backend. One supported NVIDIA GPU inference deployment through Python LLM or HTTP serving. This diagram summarizes one scheduled forward iteration, not the full token-generation loop. Historical engine builds, encoder/multimodal paths, speculative decoding, disaggregated serving and distributed parallelism are outside scope.
