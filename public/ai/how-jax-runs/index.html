Without jax.jit, JAX dispatches each operation to the device one at a time, as Python reaches it. With jax.jit, JAX traces your function into a jaxpr, lowers it to StableHLO, and hands the whole program to the XLA compiler, which fuses operations and compiles them for the target device. On CPUs and NVIDIA GPUs XLA generates code through LLVM (PTX for NVIDIA), uses Triton for some GPU kernels and NVIDIA libraries such as cuBLAS for others. Either way, JAX runs the result on the device through the PJRT runtime.

The selected path, step by step

  1. Your JAX code calls JAX: Your functions call JAX's array operations.
  2. JAX traces to jaxpr: jax.jit runs the function once with tracers and records it as a jaxpr, specialized to the argument shapes and dtypes.
  3. jaxpr lowers to StableHLO: The jaxpr is lowered to StableHLO, the XLA compiler's input language.
  4. StableHLO compiled by XLA compiler: XLA compiles the whole StableHLO program, fusing operations and specializing it for the device.
  5. XLA compiler emits LLVM IR: XLA's CPU and GPU backends emit LLVM IR for the computation.
  6. XLA compiler emits, for some kernels Triton IR: XLA:GPU generates some kernels through Triton IR emitters.
  7. XLA compiler calls, for common ops cuBLAS and cuDNN: For each operation XLA chooses between generating code and calling a library; many common operations go to cuBLAS or cuDNN.
  8. LLVM IR lowers to PTX: On NVIDIA GPUs, LLVM's NVPTX backend turns the IR into PTX.
  9. Triton IR lowers to PTX: Triton-emitted kernels also end up as PTX.
  10. PTX built into Compiled executable: The generated kernels become part of the compiled executable.
  11. cuBLAS and cuDNN called from Compiled executable: Library calls are linked into the runtime and invoked by the executable.
  12. Compiled executable run through PJRT runtime: JAX runs the compiled executable on the device through the PJRT runtime API.
  13. PJRT runtime launches on NVIDIA GPU: PJRT's GPU implementation launches the work on the NVIDIA GPU.

Where Python ends

Without jit, Python stays in charge of every operation: each jnp call is dispatched to the device on its own, so the compiler never sees more than one operation at a time.

With jax.jit, Python runs once to trace the function. From then on the computation is a jaxpr, then a StableHLO program, then an executable that XLA built for the device, and later calls with the same shapes reuse the compiled executable without running the Python body again.

How this differs from PyTorch

Both JAX and PyTorch's torch.compile capture a whole computation and compile it, and both can end up in Triton and LLVM on NVIDIA GPUs. JAX hands its program to XLA through a stable intermediate language, StableHLO, and runs it through PJRT; torch.compile captures an FX graph and generates kernels with TorchInductor. Your JAX code

JAX

framework component

The JAX library. It traces and transforms your functions, and calls out to XLA and PJRT to compile for and run on devices.

In the atlas: JAX

  • To manage hardware devices and memory, and for compilation to such devices, JAX calls out to the open XLA compiler and the PJRT runtime.
    About the project (JAX documentation) Project docs

jaxpr

intermediate representation

JAX's own intermediate language: the traced function as a list of primitive operations, specialized to the argument shapes and dtypes.

  • as a jaxpr: a function in JAX's intermediate language.
    Ahead-of-time lowering and compilation (JAX documentation) Project docs

StableHLO

intermediate representation

XLA's versioned input language, a portability layer between ML frameworks and compilers. It is an operation set, not a programming language.

  • Lower this specialized, staged-out computation to the XLA compiler's input language, StableHLO.
    Ahead-of-time lowering and compilation (JAX documentation) Project docs
  • StableHLO defines a versioned operation set (HLO = high level operations) that provides a portability layer between ML frameworks and the compiler.
    XLA architecture (OpenXLA) Project docs

XLA compiler

compiler

OpenXLA's machine-learning compiler. It optimizes the whole program, fusing operations, and generates code for the target device.

In the atlas: XLA

  • The XLA compiler takes model graphs from ML frameworks defined in StableHLO and compiles them into machine instructions for various architectures.
    XLA architecture (OpenXLA) Project docs
  • It traces the function to a jaxpr (How transformations work: tracing) and hands the whole jaxpr to XLA, which compiles it into a single optimized executable, fusing operations, eliminating temporary arrays, and specializing for your CPU, GPU, or TPU.
    Just-in-time compilation (JAX documentation) Project docs

LLVM IR

intermediate representation

XLA's CPU and GPU backends emit LLVM IR and use LLVM to generate native code.

In the atlas: LLVM

  • The CPU and GPU backends included with XLA use LLVM for low-level IR, optimization, and code generation.
    XLA architecture (OpenXLA) Project docs
  • These backends emit the LLVM IR necessary to represent the HLO computation in an efficient manner, and then invoke LLVM to emit native code from this LLVM IR.
    XLA architecture (OpenXLA) Project docs

Triton IR

intermediate representation

For some GPU kernels, XLA:GPU emits Triton IR instead of going straight to LLVM.

In the atlas: Triton

  • XLA:GPU uses a combination of "native" (PTX, via LLVM) emitters and TritonIR emitters to generate high-performance GPU kernels
    XLA:GPU architecture overview (OpenXLA) Project docs

cuBLAS and cuDNN

kernel

NVIDIA's libraries, which XLA:GPU calls for many common operations instead of generating code.

In the atlas: CUDA

  • For many common operations, XLA:GPU uses fast-performance libraries from NVIDIA, such as cuBLAS, cuDNN, and NCCL.
    XLA:GPU architecture overview (OpenXLA) Project docs
  • For every HLO instruction in the computation, XLA chooses whether to run it using a library linked into a runtime, or to codegen it to PTX.
    XLA:GPU architecture overview (OpenXLA) Project docs

PTX

intermediate representation

NVIDIA's virtual instruction set, produced through LLVM's NVPTX backend.

In the atlas: CUDA

  • The GPU backend currently supports NVIDIA GPUs via the LLVM NVPTX backend.
    XLA architecture (OpenXLA) Project docs
  • XLA:GPU uses a combination of "native" (PTX, via LLVM) emitters and TritonIR emitters to generate high-performance GPU kernels
    XLA:GPU architecture overview (OpenXLA) Project docs

XLA TPU backend

compiler

XLA compiles for TPUs too. How its TPU backend generates code is not covered by the open documentation cited here.

  • Compile the lowered HLO program to produce an optimized executable for the target device (CPU, GPU, or TPU).

Compiled executable

machine code

The optimized program for one device and one set of argument shapes. Later calls with the same shapes reuse it.

  • Compile the lowered HLO program to produce an optimized executable for the target device (CPU, GPU, or TPU).
    Ahead-of-time lowering and compilation (JAX documentation) Project docs

PJRT runtime

runtime

OpenXLA's uniform device API. Frameworks call PJRT; each device type implements it as a plug-in.

  • PJRT C API is the uniform Device API that we want to add to the ML ecosystem.
    PJRT: uniform device API (OpenXLA) Project docs
  • XLA aims for interoperability across accelerators (e.g. by ingesting StableHLO as input) and PJRT offers extensibility through a plug-in device API.
    About the project (JAX documentation) Project docs

CPU

XLA's CPU backend supports several CPU instruction sets.

  • The CPU backend supports multiple CPU ISAs.

NVIDIA GPU

hardware

XLA reaches NVIDIA GPUs through LLVM's NVPTX backend and NVIDIA libraries.

  • The GPU backend currently supports NVIDIA GPUs via the LLVM NVPTX backend.
    XLA architecture (OpenXLA) Project docs

TPU

hardware

Google's Tensor Processing Unit, one of the devices JAX compiles for.

  • Compile the lowered HLO program to produce an optimized executable for the target device (CPU, GPU, or TPU).

What this does not show

Documented paths for one JAX program run without jit and with jax.jit, on a CPU, an NVIDIA GPU, or a TPU. Multi-device sharding, Pallas kernels, AMD GPUs, PJRT plugins for other hardware, and the internals of XLA's TPU backend are out of scope. XLA's TPU backend is not described in the open-source documentation cited here, so this page shows that XLA compiles for TPUs without showing how.
