Is Ollama itself the model or the inference engine?

Ollama provides request handling, model management and compatible runners. The Go server source shows validation and scheduling before inference. The model’s weights are data consumed by an execution engine; neither the model nor the chat endpoint is a programming language.

The diagram distinguishes the service layer from the numerical runtime. This matters when answering what Ollama is written in: Go is evidence for its service implementation, while the selected native engine has its own implementation and kernels. The llama.cpp path and MLX path explain those layers in more detail.

Does every Ollama model use llama.cpp?

No. The GGUF support announcement documents llama.cpp integration alongside Ollama’s MLX engine. The MLX announcement describes an Apple-silicon path for supported architectures. Model compatibility and the installed version determine which claims apply.

The controls compare documented paths; they do not expose a real Ollama engine-selection API. A compatible GGUF route and an MLX route need not accept identical model files or support identical features. Do not infer the engine from a model’s marketing name alone.

Why does Ollama use the CPU instead of the GPU?

A CPU-only model can run in system memory. GPU execution additionally needs a compatible engine, hardware support, dependencies and enough available memory for the configured workload. The FAQ documents ollama ps and its PROCESSOR column, including fully CPU, fully GPU and mixed placement. That report is more informative than assuming a GPU installation guarantees full offload.

The CUDA choice illustrates supported offloaded work. Real deployments can use a mixture of CPU and GPU, especially when the model does not fit entirely on a device. The diagram excludes that partial-offload detail rather than asserting that all CUDA requests are GPU-only.

What changes on Apple silicon?

The documented MLX engine uses Apple’s array framework and unified-memory architecture for supported models. MLX GPU primitives are implemented using Metal, as the extension guide explains. This is different from treating a Mac as an NVIDIA CUDA system.

Other local routes can still exist on Macs. The point of the MLX branch is to show one verified engine path, not to claim every model on every Apple computer uses it. Check installed-version release notes and model support before applying this diagram to a specific deployment.

Does using the Ollama API mean my request stays local?

No. The API introduction documents both local and cloud base URLs, and local servers can also be used with cloud models. This page deliberately chooses a downloaded local model. Endpoint, model selection and serving configuration establish the execution boundary; the client library name alone does not.

How do GGUF, model size and hardware fit together?

GGUF is a model file format consumed by a compatible runtime. It does not describe one fixed processor or make all model architectures interchangeable. Memory placement and the chosen backend determine where computation occurs. This page avoids model rankings, speed promises and guessed internals, and records the engine and device conditions for each illustrated path.

What this does not show

Local text inference with downloaded models supported by the selected engine: GGUF/llama.cpp on CPU or NVIDIA CUDA, or the documented MLX engine on Apple silicon. These are version- and model-dependent illustrative paths, not a user-facing engine-switch command or a guarantee of universal model compatibility. Cloud models, AMD/Vulkan routes, partial offload, multimodal processing and detailed token sampling are not depicted.
